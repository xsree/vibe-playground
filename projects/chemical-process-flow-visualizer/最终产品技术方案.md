# 工艺流程可视化应用最终技术方案

## 1. 技术目标

建设一个以结构化工艺图谱为核心的 Web 应用，实现：

```text
工艺描述文本
→ LLM 结构化提取
→ JSON Schema 校验与规范化
→ 设备形状映射
→ 无重叠自动布局
→ 可编辑设备和粘连管线
→ 保存 JSON/YAML
→ 导出 PNG/SVG/PDF
```

技术设计应保持轻量，不引入 P&ID、工程计算、复杂审计和企业权限等超出产品范围的系统。

## 2. 现有输入文件

当前目录已有：

- `process-flow.schema.json`：Draft 2020-12 数据 Schema。
- `pendimethalin-process.test.json`：包含52个节点和57条管线的完整测试数据。
- `MVP方案.md`：第一版开发范围和验收要求。
- `最终产品方案.md`：最终产品功能与交互定义。

实施时应以这些文件为起点，不重新发明另一套不兼容的数据结构。

## 3. 总体架构

```text
┌────────────────────────────────────────────────────────────┐
│                       Web 前端                             │
│                                                            │
│  文本/JSON编辑器  画布编辑器  属性面板  设备形状库  导出  │
│          │             │          │          │             │
│          └─────────────┴──────────┴──────────┘             │
│                         │                                  │
│                 ProcessFlowDocument                        │
│                         │                                  │
│       Schema校验 ─ 规范化 ─ 图检查 ─ 布局转换              │
└─────────────────────────┬──────────────────────────────────┘
                          │ HTTPS
┌─────────────────────────▼──────────────────────────────────┐
│                      轻量服务端                            │
│                                                            │
│        LLM代理  提示词管理  结构化输出重试  可选文件保存   │
```

核心原则：画布、LLM 和导出模块都围绕同一个 `ProcessFlowDocument` 工作。

## 4. 推荐技术栈

### 4.1 前端

- React
- TypeScript
- Vite
- `@xyflow/react`：节点、端口、选择、拖动和连线交互。
- `elkjs`：分层自动布局及初始正交路由。
- Ajv 2020：Draft 2020-12 JSON Schema 校验。
- Zustand：编辑器状态。
- Zundo 或自建 command history：撤销和重做。
- Monaco Editor 或 CodeMirror：JSON/YAML 编辑。
- `yaml`：JSON/YAML 转换。
- `html-to-image`：PNG 导出。
- SVG DOM 序列化：SVG 导出。
- 浏览器打印或 SVG 转 PDF：PDF 导出。
- Vitest：单元测试。
- Playwright：端到端测试。

### 4.2 服务端

优先选择与前端一致的 TypeScript 技术栈：

- Node.js
- Fastify 或轻量 Express
- Zod：服务端请求校验。
- OpenAI SDK 或目标 LLM 的官方 SDK。

服务端只负责：

- 隐藏 LLM API 密钥；
- 拼装系统提示词和 Schema；
- 请求结构化输出；
- 对无效结果进行有限次数修复重试；
- 返回结构化 JSON 和错误信息；
- 可选保存用户文件。

如果第一版只在本机使用，可以先实现单进程本地服务，不必建设账号和数据库。

## 5. 核心领域模型

建议从 JSON Schema 生成或手工维护对应 TypeScript 类型：

```ts
type NodeKind = "equipment" | "source" | "sink" | "junction";
type PortDirection = "in" | "out" | "bidirectional";
type Routing = "straight" | "orthogonal";

interface ProcessFlowDocument {
  schemaVersion: "1.0";
  title: string;
  description?: string;
  nodes: ProcessNode[];
  edges: ProcessEdge[];
  layout: ProcessLayout;
  settings: ProcessSettings;
}

interface ProcessNode {
  id: string;
  kind: NodeKind;
  tag: string | null;
  name: string;
  equipmentType: string | null;
  shapeKey: string;
  quantity?: number;
  ports: ProcessPort[];
  attributes: Record<string, unknown>;
}

interface ProcessPort {
  id: string;
  direction: PortDirection;
  role: string;
  label?: string;
}

interface ProcessEdge {
  id: string;
  source: { nodeId: string; portId: string };
  target: { nodeId: string; portId: string };
  label: string;
  streamType: string;
  material: {
    name: string;
    phase?: string | null;
    components?: string[];
  };
  attributes: Record<string, unknown>;
}
```

`equipmentType`、`shapeKey`、端口 `role` 和管线 `streamType` 保持开放字符串。应用可以识别常用值，但不能因为遇到新值而拒绝整个文件。

## 6. 数据处理流水线

### 6.1 输入

系统支持三种输入：

1. 工艺描述文本；
2. JSON；
3. YAML。

JSON/YAML 直接进入校验流程。工艺文本先进入 LLM 提取流程。

### 6.2 LLM 结构化提取

LLM 提示词应明确：

- 只输出符合 Schema 的 JSON；
- 提取物料来源、设备、去向和连接；
- 不输出坐标；
- 不输出 SVG、HTML 或前端代码；
- 有位号时保留位号；
- 没有位号时生成唯一随机 ID；
- 不确定设备使用原文名称和通用形状；
- 不凭空生成设备位号；
- 明确串联的设备展开；
- 未明确内部连接的同类设备组聚合并设置 `quantity`；
- 所有边必须指向已存在的节点和端口；
- 不明确去向应生成 `sink` 边界节点，不能生成悬空边。

推荐两阶段调用：

```text
第一阶段：提取设备、来源和去向
第二阶段：基于确定的节点 ID 提取连接关系
```

流程较小时可以一次调用，但仍须经过本地规范化和校验。

### 6.3 Schema 校验

使用 Ajv 2020：

```ts
import Ajv2020 from "ajv/dist/2020";
import schema from "./process-flow.schema.json";

const ajv = new Ajv2020({
  allErrors: true,
  strict: true
});

const validate = ajv.compile(schema);
```

校验失败时保留当前有效画布，不得用无效数据覆盖编辑器状态。

### 6.4 规范化

`normalizeProcessFlow` 负责：

- 为无 ID 节点生成 `eq_<short-uuid>`；
- 为无 ID 管线生成 `flow_<short-uuid>`；
- 为缺少端口的设备补充端口；
- 将非法 `shapeKey` 映射为 `generic.process`；
- 为 `quantity` 补默认值 `1`；
- 清理首尾空格；
- 将重复 ID 改为唯一 ID，并同步更新引用；
- 将空的 `attributes` 补为 `{}`；
- 将缺少的布局对象补为自动布局状态。

规范化不应修改已有合法位号和设备名称。

### 6.5 图语义检查

JSON Schema 无法完成跨对象引用校验，因此需要单独实现：

- 节点 ID 唯一；
- 管线 ID 唯一；
- 同一节点的端口 ID 唯一；
- 管线源节点和目标节点存在；
- 管线源端口和目标端口存在；
- 源端口方向不是 `in`；
- 目标端口方向不是 `out`；
- 布局中引用的节点和管线存在；
- 可选检查孤立节点；
- 可选检查是否存在从主要原料到产品去向的路径。

检查结果分为：

- `error`：无法渲染或会破坏连接；
- `warning`：可以渲染，但可能需要用户确认。

## 7. 形状系统

### 7.1 形状注册表

```ts
interface ShapeDefinition {
  key: string;
  component: React.ComponentType<ShapeProps>;
  defaultSize: { width: number; height: number };
  portPresets: PortPreset[];
  aliases?: string[];
}

const shapeRegistry = new Map<string, ShapeDefinition>();
```

每个形状定义：

- SVG 组件；
- 默认宽高；
- 默认端口位置；
- 可匹配的设备类型关键词；
- 可选的最小尺寸。

### 7.2 形状解析

解析顺序：

```text
节点指定 shapeKey 且已注册
→ 直接使用

shapeKey 未注册
→ 根据 equipmentType 和 name 匹配别名

仍未匹配
→ generic.process
```

LLM 的 `shapeKey` 只是建议，最终由本地注册表决定是否可用。

### 7.3 SVG 约束

- 所有形状使用统一 `viewBox` 体系。
- SVG 只负责设备轮廓，不负责节点选择框、标签和端口交互。
- 颜色使用 CSS 变量，支持浅色和深色主题。
- 设备名称和位号使用 HTML 标签层，避免 SVG 文本测量困难。
- 端口由画布组件渲染，不能把端口画死在 SVG 路径中。

## 8. 自动布局

### 8.1 ELK 输入转换

将领域模型转换为 ELK 图：

- 节点使用形状注册表提供的实际宽高；
- 端口作为 ELK ports；
- 管线作为 ELK edges；
- 主流程边设置较高优先级；
- 气相和废水支路通过端口侧约束引导方向；
- 聚合设备作为单个节点参与布局。

推荐初始参数：

```ts
const layoutOptions = {
  "elk.algorithm": "layered",
  "elk.direction": "RIGHT",
  "elk.edgeRouting": "ORTHOGONAL",
  "elk.spacing.nodeNode": "80",
  "elk.layered.spacing.nodeNodeBetweenLayers": "160",
  "elk.portConstraints": "FIXED_SIDE",
  "elk.separateConnectedComponents": "true"
};
```

### 8.2 端口侧规则

- `material` 输入：左侧；
- `material` 和 `product` 输出：右侧；
- `gas` 输出：上侧；
- `waste` 输出：下侧；
- `utility` 输入：上侧或左侧；
- `recycle`：根据连接方向决定，允许走图外侧。

### 8.3 防重叠

初始布局防重叠依赖真实节点宽高和 ELK spacing。

人工拖动时使用矩形碰撞检测：

1. 根据候选坐标计算节点包围盒；
2. 与其他节点包围盒检测相交；
3. 无碰撞则保存位置；
4. 有碰撞则寻找最近可用位置，或恢复拖动前位置。

新增设备使用相同的空位搜索逻辑。

### 8.4 管线避障

React Flow 的普通折线只能保证端点粘连，不能保证路径始终避开其他节点。

实现层级：

- 初始布局：使用 ELK 返回的折点；
- 拖动节点：对与该节点相连的管线执行局部正交重路由；
- 简单场景：曼哈顿路径加节点矩形避障；
- 复杂场景：引入专用正交避障路由器，或对局部子图重新运行 ELK。

手动折点存入 `layout.edges[edgeId].waypoints`。用户修改折点后，该边进入手动路由状态，普通节点移动只调整首尾段。

## 9. 画布编辑器

### 9.1 React Flow 数据适配

领域模型不能直接等于 React Flow 数据结构。建立适配层：

```text
ProcessFlowDocument
  ↕ adapter
React Flow nodes / edges
```

这样将来替换画布库时，不需要迁移保存文件。

### 9.2 自定义节点

自定义节点负责：

- 渲染设备 SVG；
- 渲染位号、名称和数量；
- 根据端口定义创建 handles；
- 显示选中、错误和锁定状态；
- 报告真实尺寸给布局系统。

### 9.3 自定义管线

自定义管线负责：

- 直线和正交折线；
- 箭头；
- 物料标签；
- 手动折点；
- 选中和重连交互；
- 不同 `streamType` 的线型表达。

### 9.4 状态管理

Zustand store 建议拆分为：

```ts
interface EditorState {
  document: ProcessFlowDocument;
  selection: SelectionState;
  viewport: ViewportState;
  validation: ValidationState;
  generation: GenerationState;
  history: HistoryState;
}
```

不要将鼠标悬停、临时拖动坐标等高频瞬态状态写入领域文档。

### 9.5 撤销和重做

记录领域操作，不记录每一个鼠标移动事件。典型命令包括：

- 添加节点；
- 删除节点；
- 更新节点；
- 移动节点；
- 添加管线；
- 删除管线；
- 重连管线；
- 更新管线；
- 应用自动布局。

拖动节点从按下到释放只形成一条历史记录。

## 10. LLM 服务设计

### 10.1 API

```http
POST /api/generate-process-flow
Content-Type: application/json

{
  "title": "二甲戊灵合成流程",
  "text": "...工艺描述..."
}
```

响应：

```json
{
  "document": {},
  "warnings": [],
  "attempts": 1
}
```

### 10.2 服务端处理

```text
请求校验
→ 构建提示词
→ 调用结构化输出
→ Schema 校验
→ 图引用校验
→ 必要时携带错误进行一次修复调用
→ 返回文档和警告
```

修复次数必须有限，防止请求无限循环。

### 10.3 安全

- API 密钥只存在服务端环境变量中。
- 限制文本长度和请求频率。
- 不执行 LLM 输出中的代码。
- 不渲染 LLM 输出的任意 HTML 或 SVG。
- `shapeKey` 只能选择本地注册的组件。
- 导入 JSON 时限制节点数、管线数和字符串长度。

## 11. 文件保存

### 11.1 本地优先

MVP 和单机版可以采用：

- 浏览器 IndexedDB 自动保存当前草稿；
- JSON 文件作为正式可编辑文件；
- 文件导入和下载完成跨会话使用。

### 11.2 可选云端保存

最终产品如需要跨设备使用，可增加：

- 项目表；
- 当前文档 JSON；
- 创建和更新时间；
- 可选缩略图。

不需要引入复杂版本历史，除非后续需求明确提出。

## 12. 导出方案

### 12.1 JSON/YAML

- 导出完整 `ProcessFlowDocument`。
- 保存语义数据和当前布局。
- YAML 由 JSON 数据转换，不维护第二套模型。

### 12.2 PNG

- 计算所有节点和管线的内容边界。
- 临时调整视口覆盖完整画布。
- 按用户设置的倍率生成图片。
- 导出完成后恢复原视口。

### 12.3 SVG

直接导出画布中的 SVG 管线还不够，因为 React 节点通常是 HTML。推荐实现独立的导出渲染器：

```text
ProcessFlowDocument + layout
→ 纯 SVG 设备形状、文字和管线
→ SVG 文件
```

独立导出渲染器可以保证矢量输出不依赖当前 DOM 缩放状态。

### 12.4 PDF

- 优先以 SVG 为源生成 PDF。
- 支持适应单页。
- 支持 A4、A3、A2、A1 和自定义页面。
- 超大画布支持分页或缩放。
- 保持文字和线条清晰。

## 13. 性能策略

- 以200个节点、400条管线作为第一阶段性能目标。
- React 节点组件使用 memo，避免无关节点重新渲染。
- 高频拖动状态和领域文档更新分离。
- ELK 在 Web Worker 中执行，避免阻塞界面。
- 大图中隐藏非必要端口标签。
- 只对受影响的管线执行局部重路由。
- 保存和导出操作使用快照，不阻塞继续编辑。

## 14. 错误处理

### LLM 错误

- 网络失败：保留输入文本和当前画布。
- 输出不是 JSON：允许修复重试。
- Schema 不通过：显示字段错误。
- 引用不存在：显示具体管线和节点 ID。

### 渲染错误

- 未知形状：回退到 `generic.process`。
- 缺少布局：自动布局。
- 局部路由失败：回退为简单正交线或直线。
- 导出失败：不影响当前编辑内容。

### 文件错误

- 解析失败时不替换当前文档。
- 文件过大时提示限制。
- Schema 版本不支持时提示用户，不静默转换。

### 15.1 单元测试

- Schema 校验成功和失败用例。
- 随机 ID 生成。
- 默认端口补充。
- 未知形状回退。

- JSON/YAML 双向转换。
- 领域模型与 React Flow 数据适配。
- 布局结果写回。
- 矩形碰撞检测。

### 15.2 布局测试

- 串联流程。
- 多入口汇合。
- 一对多分支。
- 多对一汇合。
- 气相上支路。
- 废水下支路。
- 回收流。
- 多个断开流程分量。
- 不同尺寸设备混合。
- 聚合设备组。

所有布局测试检查节点包围盒不相交。

### 15.3 编辑器测试

- 拖动设备后管线仍连接端口。
- 添加和删除节点。
- 删除节点同步删除关联管线。
- 管线重新连接。
- 直线和折线切换。
- 撤销和重做。
- 保存后重新加载恢复位置。

### 15.4 端到端测试

使用 `pendimethalin-process.test.json`：

1. 导入测试文件；
2. 自动生成布局；
3. 确认52个节点和57条管线；
4. 检查不存在节点重叠；
5. 移动一台设备；
6. 检查管线保持连接；
7. 保存 JSON；
8. 重新载入；
9. 导出 PNG；
10. 检查输出包含完整画布。
